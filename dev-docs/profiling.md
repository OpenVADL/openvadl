# Profiling OpenVADL

Using a Profiler is a necessary step when trying to optimize a large piece of
software such as OpenVADL. The setup necessary to use them is however not
always trivial, or at least not easy to find. This file's purpose is then to
collect information regarding the setup and use of profilers for developing
OpenVADL.

This guide profiles the OpenVADL compiler not the artifacts the generated by 
OpenVADL (at the time of writing no such documents exist, but they should be 
extra guides).

## Some Basics

The Java ecosystem world is heavily dominated by long-lived applications
like webservers and GUI applications. In that regard a short-lived compiler
like openvadl is the black sheep and the default options most debuggers in 
that space, ship with are suboptimal for OpenVADL.

Most of the time it is just that samples are too corse (too far apart).

For OpenVADL we mostly care about the GraalVM native image performance 
since it is in all of our benchmarks faster than the JVM based builds.
However, compiling a native image takes quite some time and so it 
sometimes makes sense to do a JVM profile to get a rough estimate first.
Just be aware that some things that are slow on the JVM are instant on 
the native image as they move to build-time, like class loading.

We'll go into two profilers here. Async profiler is the best one for 
our usecase. For JVM builds we only go into its setup. For Native images
async is only really usable on linux as on macOS the names are mangeled and
hard to reason which method is what. Therefore, we also go into the JFR profiler
which is too corse for most cases as it only allows at the highest frequency
a sample every 1ms.

## JVM profiler with IntelliJ IDEA 

On the JVM we recommend setting up two profilers, one for cpu profiling
and one for memory profiling.

1. Go to Settings -> Build, Execution, Deployment -> Java Profiler.
2. Click the "Async Profiler" button. This creates a new Profiler Profile.
    1. Set "Agent Options" to `event=alloc,alloc=32k`. This will be your
       memory allocation profiler.
    2. Set a name of your choosing.
3. Click "Async Profiler" again to create another Profiler Profile
    1. Set "Agent Options" to `event=wall,interval=200us,jfrsync=profile`. This
       will be your CPU profiler
    2. Set a name of your choosing.
4. Leave the settings by clicking "Ok"
5. Click the three dots next to the "Run" button in the top right.
6. Click "Profile <your-target> with <your-profiler>".


## Native Image profiler with JFR

JFR is not the right profiler for quick-lived applications like OpenVADL. If you are on Linux I strongly recommend to
with Async Profiler. For macOS this works but the names in the profile will be mangled and hard to read/trace back.
For Windows this straight up isn't an option.

For native image you need to enable profiling support at compile time. This is already setup as the `native-profile`
target. 

To compile and run it with.

```bash
./gradlew :vadl-cli:nativeProfileCompile

./vadl-cli/build/native/nativeProfileCompile/openvadl-profile \
  -XX:FlightRecorderOptions=stackdepth=256 \
  -XX:StartFlightRecording=filename=native.jfr,settings=config/profiling/cpu.jfc,dumponexit=true \
  check sys/huge/huge.vadl --decoder skip=all    # <-- Replace this with what you want to profile

# This step is only needed if you want to view the profile in IntelliJ
# and generates the file native-intellij.jfr
python3 scripts/jfr_intellij_compat.py native.jfr
```

The running the profile build with the options listed produces the profile recording `native.jfr`. 
This file is a standard format and there are multiple visualizers, including one built into IntelliJ.

However, the native image generated profile marks all functions with `AOT compiled` which at the time of writing 
confuses IntelliJ. This reults in the profile visualizer not resolving any classes and so two methods with the same
name are always collapsed into one even if they are overloaded, or on entirely other classes.

As a workaround the script `scripts/jfr_intellij_compat.py` exists which generates the profile `native-intellij.jfr` 
where all methods are marked `JIT compiled` with which IntelliJ can work again.

In general the profiler included in native images lacks some features, provides less accuracy (no lower than 1ms 
sampling intervals) and runs faster which means that even fewer samples are recorded.

## Native Image with async profiler

This workflow isn't available on Windows, and on macOS the method names in the profile are mangled. This means
every method has a hash postfix and two methods with the same name in the same class have the same name only to be
distinct by the hash but reasoning which method links to which Java method may be hard to impossible.

For native image you need to enable profiling support at compile time. This is already setup as the `native-profile`
target.

```bash
./gradlew :vadl-cli:nativeProfileCompile
```

### Install async-profiler

You need to install the async profiler seperatly.

On macOS, install the [Homebrew formula](https://formulae.brew.sh/formula/async-profiler):

```bash
brew install async-profiler
export ASYNC_PROFILER_HOME="$(brew --prefix async-profiler)"
```

For Linux, download and extract the matching `linux-x64` or `linux-arm64` package
from the same release, then set `ASYNC_PROFILER_HOME` to its extracted directory.
The library must match the executable's architecture.

### Record a profile

On macOS:

```bash
DYLD_INSERT_LIBRARIES="$ASYNC_PROFILER_HOME/lib/libasyncProfiler.dylib" \
ASPROF_COMMAND="start,event=cpu,interval=200us,cstack=fp,file=native-async.jfr" \
  ./vadl-cli/build/native/nativeProfileCompile/openvadl-profile \
  check sys/huge/huge.vadl --decoder skip=all
```

On Linux:

```bash
LD_PRELOAD="$ASYNC_PROFILER_HOME/lib/libasyncProfiler.so" \
ASPROF_COMMAND="start,event=cpu,interval=200us,cstack=fp,file=native-async.jfr" \
  ./vadl-cli/build/native/nativeProfileCompile/openvadl-profile \
  check sys/huge/huge.vadl --decoder skip=all  # <-- Replace this with what you want to profile
```

Open **`native-async.jfr`** directly in IDEA or another JFR viewer.
